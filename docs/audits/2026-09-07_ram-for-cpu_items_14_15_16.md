## 15 — stray `println!()` in `/metrics` render (`13e7e2f`)

**Bug, not optimization.** `render_prometheus` ended with `println!();` intended as `out.push('\n')`. Every Prometheus scrape (15s default, forever) fired a stdout write syscall into journald and leaked a stray line into logs.

**Fix:** deleted. Every emit stanza already ends in `\n`, so the correct output has no trailing blank line — pure deletion, zero added code.

## 16 — cached `/metrics` text + seq-invalidated dashboard JSON (`19aea72`)

~90KB of RAM removes all per-request re-cooking on three hot read paths:

1. **`/metrics` text cache** — 1s TTL (`Mutex<Option<(Instant, String)>>`). Counters move on a second grain, so identical text was re-rendered (~100 allocations) per scrape. Same pattern `get_system_usage` already used in the file. Documented compromise: staleness ≤ 1s; `metrics_cache:clear()` on every write path keeps unit tests deterministic.

2. **Block-log JSON** and **batch-history JSON** — sequence-counter caches. Each `get_block_log`/`get_batch_history` previously cloned up to 1000 records × 3 heap `String`s (~3k allocations) + serde re-serialization per 2s dashboard poll. Now: `block_seq`/`batch_seq` `AtomicU64` bumped **inside the existing write-path locks** (`record_block`, `prune_and_record`, `record_batch`), and the rendered JSON held as `Arc<str>`. A warm poll is a refcount clone.

   **The race that matters, closed:** the seq is read **before** the ring is cloned; the cache is only stamped if the seq is unchanged after render. A write that races mid-render leaves the previous stamp lower than the observed seq → permanently rejected. Stamping after render would let that write's data hide behind stale text forever. `SeqClock` (shared `AtomicU64` + `Mutex<Option<…>>`) keeps the invariant in one place.

   Dashboard handlers (`api_metrics`, `api_history_batches`, `api_history_blocks`) now serve the cached strings; content-type unchanged, byte-for-byte same JSON on a miss.

## 14 — O(due) expiry ring + evict gate (`bcffe27`)

### Enforcement: second-bucket ring (the real fix)

`expire_due` ran a full retain over all pending TTL blocks every 250ms — O(all pending) per tick to normally find zero due; under a 64k-block flood that is 4 full sweeps/second.

Replaced `Vec<(Instant, IpAddr)>` with:

```rust
expirations: HashMap<IpAddr, (u64, usize)>,   // IP -> (bucket, position)
buckets:     BTreeMap<u64, Vec<IpAddr>>,     // whole-second deadline -> cards
```

- **Drain:** pop only buckets whose whole-second deadline passed. O(due), zero touch otherwise.
- **Refresh (re-block):** `schedule_expiration` detaches first (O(1)), so a TTL update **moves the card** — never stacks a stale duplicate. The rejected BinaryHeap design couldn't do this without lazy-delete bookkeeping.
- **Swap-remove surgery:** removing a card from the middle of a bucket moves the last element into its slot; that neighbour's position index is fixed up in the same operation.
- **Never early:** `bucket_of` ceils the deadline to whole seconds, so a bucket only drains after the exact deadline passed.
- **Self-heal guard:** if the indexed slot holds a different IP (index drift from a bug elsewhere), the code scans the bucket for the right card instead of silently unblocking the wrong host — fail-safe against a stranded index.
- **`check_ring_invariant()`** (test-only) asserts every `(bucket,pos)` points at its IP and total card count equals map size; exercised by a churn storm test.

**Deviation from the ~4MB sketch (deliberate):** a fixed 320-slot ring assumed TTLs ≤ 300s. Verified `block_ttl_secs` defaults to **3600s** — a sparse `BTreeMap` keyed by second costs one entry per bucket with live deadlines instead of pre-allocating for the longest TTL. Same O(due), correct for unbounded TTLs.

### Storage: 8 bytes instead of 4MB

`evict_expired()` walked the entire store every 60s (collect up to 64k keys, rehash each). Ground check at live HEAD: **no production caller ever passes `Some(ttl)` to `Store::insert`** — every path inserts `None` and `update_ip` clears `expires_at`. The store has *nothing that can expire*; the walk was 100% overhead, 0% eviction.

Fix: an 8-byte `ttl_entries: Arc<AtomicU64>` (incremented when a TTL-bearing entry is newly born — fresh insert *or* non-TTL→TTL replacement, with compensating decrements on capacity-reject rollback, `evict_batch` skips, and `remove`). `evict_expired` early-returns when the count is zero. The full sweep **stays as the correctness backstop** for any future TTL writer; a bookkeeping bug can never strand an entry. Maintenance cadence untouched.

Skipped: a second ring on the store side. When nothing sets TTLs, an index over `expires_at` is machinery for a condition that never occurs. Add it (real cost, real design) the day someone passes `Some(ttl)` in prod.

## Honest caveats

- CPU deltas are analytical (allocation counts, syscall counts, sweep frequencies), **not measured**. `scripts/bench` against `master` vs `bd2ec0b` prices them post-merge.
- `/metrics` staleness ≤ 1s and dashboard-JSON staleness = one write-path hop are the intended trade; both were stated and accepted at design.
- WAL replay schedules no TTL (pre-existing): replayed blocks stay blocked until manual unblock. Out of scope here; flagged for a correctness pass, not silently mixed into a perf commit.
